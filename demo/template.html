The lexer, as a transition table

Each row is the state of the previous character. Each column is the class of the next one. The cell is the new state, shown in the color the character will be drawn in.

The highlighted row is the start state. It becomes the fallback rules at the end of the lookup. Faded cells give the same answer as the fallback, so the compiler emits no rule for them.

How a font can run a lexer

1

Every character gets a copy of its glyph for each state it can be in, named like {{VARIANT_EXAMPLE}}. Copies are composites that point at the original outline, so they cost a few bytes each.

2

A chaining contextual lookup walks the text left to right. Its backtrack context sees glyphs it already replaced, so the previous glyph's copy carries the automaton's state forward. One rule per table cell:

3

A second lookup recolors whole identifiers that spell a keyword. {{WORDS_NOTE}}

4

Each colored copy gets a COLR record that paints the original outline with a palette entry. The font carries a light and a dark palette.

Limits of this prototype

  • State lives only within one shaping run. Browsers start a new run at each line and wherever a fallback font takes over, so multi-line strings and comments lose their state. With some base fonts, Safari also starts one at a change of script; the compiler warns about those and can merge their scripts.
  • Coloring is decided as each character is read, with one glyph of lookahead for words and for states that ask for it. Anything that needs more context needs another pass, and a finite automaton can't track nesting.
  • Tested with HarfBuzz (Chrome, Firefox, Android) and Core Text (Safari, native Mac apps), shaping every case through both and comparing each glyph with a reference lexer.
  • The base font's own ligatures and alternates are removed, because they would replace glyphs the lexer needs to see. Its kerning and mark positioning are kept.
